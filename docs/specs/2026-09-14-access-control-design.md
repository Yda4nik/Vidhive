# Дизайн: аккаунты, вход и роли доступа

Дата: 2026-09-14
Статус: утверждён (ожидает реализации)
Связано с: критерий 14 задания («SSH-доступ с ролями»), Фаза 3 (SSH-развёртывание — за ролью administrator).

## 1. Цель

Добавить в координатор аутентификацию пользователей (вход по логину и паролю)
и разграничение прав по трём ролям. Веб-интерфейс и управляющий REST API
доступны только после входа; машинные ручки агентов защищены отдельным токеном.
Секретов в коде/логах нет — всё из переменных окружения.

Не входит в этот дизайн (отдельно, позже): SSH-развёртывание агентов (Фаза 3),
TLS/HTTPS, сброс пароля по почте, 2FA.

## 2. Ролевая модель

Три роли по возрастанию прав: `viewer < operator < administrator`.

| Действие | viewer | operator | administrator |
|---|:--:|:--:|:--:|
| Панель, библиотека, просмотр/стрим видео | ✅ | ✅ | ✅ |
| Создать/старт/пауза/продолжить/стоп/повтор задания, `/add` | | ✅ | ✅ |
| Удалить видео, метки/группы (создать/переименовать/удалить/назначить) | | ✅ | ✅ |
| Управление серверами: удаление / распределение (позже — SSH) | | | ✅ |
| Управление пользователями (`/users`) | | | ✅ |

Роль сравнивается по рангу: `viewer=1, operator=2, administrator=3`.
Проверка `require_role(min)` пропускает, если `rank(user) >= rank(min)`.

## 3. Аутентификация

### 3.1 Сессии
Подписанная cookie через Starlette `SessionMiddleware` (секрет из
`VIDHIVE_SECRET_KEY`). В сессии хранится только `user_id`. Логаут очищает сессию.
Без серверного хранилища сессий (для стенда достаточно; ревокация — вне объёма).

### 3.2 Хэш паролей
`hashlib.pbkdf2_hmac("sha256", password, salt, iterations)` со случайной солью
на пользователя. Формат в колонке `users.password_hash` (уже существует, `String(255)`):
`pbkdf2_sha256$<iterations>$<salt_b64>$<hash_b64>`. Проверка —
constant-time сравнение (`hmac.compare_digest`). Без сторонних библиотек.

### 3.3 Первый админ (bootstrap)
При старте координатора (lifespan): засеять роли `viewer/operator/administrator`,
если их нет; и если в таблице `users` нет ни одного пользователя — создать
администратора из `VIDHIVE_ADMIN_USER` / `VIDHIVE_ADMIN_PASSWORD`. Если эти
переменные не заданы — пользователей не создаём и пишем предупреждение в лог
(вход будет невозможен, пока админ не задан) — секрет по умолчанию не хардкодим.

### 3.4 Токен агента
Машинные ручки `POST /api/workers/{register,lease,heartbeat,progress,complete,fail}`
требуют заголовок `X-Agent-Token`, равный
`VIDHIVE_AGENT_TOKEN`. Плавный выкат: **если `VIDHIVE_AGENT_TOKEN` пуст — проверка
выключена** (поведение как сейчас), в лог пишется предупреждение. Агент шлёт токен
из своего env в каждом запросе к координатору.

## 4. Enforcement (где и как проверяем)

- Зависимость `get_current_user(request, session)` читает `user_id` из cookie-сессии,
  грузит пользователя и его роль. Нет сессии → пользователь не аутентифицирован.
- Зависимость-фабрика `require_role(min_role)`:
  - API-маршруты: нет входа → `401`; роль ниже → `403` (JSON).
  - Веб-страницы: нет входа → редирект `303 → /login?next=<path>`; роль ниже →
    страница `403` (человекочитаемая). Реализуется через собственное исключение
    `WebAuthError`, перехватываемое обработчиком, который для HTML отдаёт редирект,
    а для API — JSON.
- Токен агента: отдельная зависимость `require_agent_token` на машинных ручках.
- `GET /events/stream`, фрагменты, страницы просмотра — минимум `viewer`.
- Статика (`/static`), `/login`, `/health` — без входа.

Карта защиты по существующим маршрутам:

| Маршрут | Минимальная роль / доступ |
|---|---|
| `/`, `/library`, `/player/{id}`, `/watch/{id}`, `/fragments/*`, `/events/stream`, `GET /api/workers`, `GET /api/workers/{id}`, `GET /api/jobs*`, `GET /api/library*` | viewer |
| `/jobs`, `/add`, `/jobs/{id}/{action}`, `/api/jobs/*` (мутации), `/api/library/*` (мутации), `/api/groups*` | operator |
| `/servers`, `/fragments/servers`, `/servers/{id}/delete`, `DELETE /api/workers/{id}` | administrator |
| `/users*`, `/api/users*` | administrator |
| `/api/workers/{register,lease,heartbeat,progress,complete,fail}` | токен агента |
| `/login`, `/logout`, `/health`, `/static/*` | без входа |

## 5. Данные

Таблицы уже есть в схеме (миграция `4f9b48b05fc8_initial_schema`): `users`
(`id, username unique, password_hash, created_at`), `roles` (`id, name unique`),
`user_roles` (`user_id, role_id`). Новых колонок/миграций не требуется. Каждому
пользователю назначается ровно одна роль (через `user_roles`).

## 6. Страницы и маршруты (новое)

- `GET /login` — форма (логин, пароль, скрытый `next`).
- `POST /login` — проверка → ставит сессию → редирект на `next` или `/`.
  Неверные данные → та же форма с ошибкой (без утечки, «неверный логин или пароль»).
- `POST /logout` — очистка сессии → `/login`.
- `GET /users` (admin) — список пользователей с ролями; формы: создать
  (логин/пароль/роль), сменить роль, сбросить пароль, удалить (нельзя удалить
  самого себя и последнего администратора).
- `POST /users`, `POST /users/{id}/role`, `POST /users/{id}/password`,
  `POST /users/{id}/delete` — управляющие действия (admin).

Шапка (`base.html`): показывает текущего пользователя и роль, кнопку «Выйти»;
ссылки/кнопки, недоступные роли, скрываются (⚙ Управление и «Пользователи» —
только admin; форма создания заданий и кнопки удаления — от operator). Скрытие —
только UX; настоящий гейт на сервере.

## 7. Конфигурация (env, добавить в `deploy/.env.example`)

- `VIDHIVE_SECRET_KEY` — подпись cookie-сессии (обязателен в проде; для локали/тестов
  допускается дефолт-заглушка с предупреждением).
- `VIDHIVE_AGENT_TOKEN` — общий секрет агентов (пустой = проверка выключена).
- `VIDHIVE_ADMIN_USER`, `VIDHIVE_ADMIN_PASSWORD` — первый админ при пустой БД.

Секреты в код/логи не попадают; в логах — только факт создания/входа, без значений.

## 8. Порядок выката (важно, чтобы не уронить стенд)

1. Выкатить код: агент умеет слать `X-Agent-Token` (из env, пустой ⇒ не шлёт),
   координатор проверяет токен только если он задан. Пока `VIDHIVE_AGENT_TOKEN`
   пуст — всё работает как раньше.
2. Задать `VIDHIVE_ADMIN_USER/PASSWORD` и `VIDHIVE_SECRET_KEY` в `deploy/.env`,
   перезапустить координатор → создаётся админ, вход включён.
3. Задать `VIDHIVE_AGENT_TOKEN` в `.env` для координатора и агентов, перезапустить →
   машинные ручки закрыты токеном.

## 9. Тестирование

- Хэш паролей: hash/verify, неверный пароль отклоняется, соль различается.
- Bootstrap: роли засеяны; админ создаётся при пустой БД; повторный старт не дублирует.
- Вход/логаут: верные/неверные данные; редирект `next`.
- Разграничение: viewer не может создать задание (403/редирект); operator не может
  удалить сервер; admin может всё; неаутентифицированный → 401/редирект.
- Токен агента: при заданном токене register без заголовка → 401, с заголовком → ок;
  при пустом токене — открыто (обратная совместимость).
- Существующие тесты: общая фикстура логинится админом; добавить фикстуры на роли.

## 10. Открытые допущения

- Одна роль на пользователя (не набор). Достаточно для трёх уровней.
- Нет «запомнить меня»/срока сессии сверх cookie по умолчанию.
- TLS завершается вне приложения (реверс-прокси стенда) — вне объёма.
