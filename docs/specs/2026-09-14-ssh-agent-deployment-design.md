# Дизайн: развёртывание и снос агента по SSH («подключение серверов через веб»)

Дата: 2026-09-14
Статус: утверждён (ожидает реализации)
Фаза 3. Опирается на роли ([[access-control]]): вся фича — только для `administrator`.

## 1. Цель

Администратор через веб добавляет в сеть **новый пустой Linux-сервер**: заполняет
форму с данными подключения (SSH), а координатор сам разворачивает на нём агента
(нативно, без Docker на цели) и запускает как службу. Схема **1 сервер = 1 агент**.
Также — обратная операция: **полный снос** всего, что развернули на сервере.

Не входит: Windows-цели, кластеры, авто-обновление агента.

## 2. Сценарий

1. Admin открывает `/servers` → «Добавить сервер» → форма.
2. Координатор по SSH (ключ из формы, **одноразово, не хранится**) выполняет один
   bootstrap-скрипт на цели: ставит зависимости, кладёт код агента, поднимает
   systemd-службу.
3. Агент стартует, регистрируется у координатора → появляется в списке «online».
4. Живой лог развёртывания виден в вебе.
5. Позже admin может «Удалить сервер»: из пула (как сейчас) и опционально —
   **полностью снести с машины** (повторно вводит ключ → teardown-скрипт).

## 3. Сеть (обязательно учесть)

- Удалённый агент должен достучаться до координатора: `VIDHIVE_COORDINATOR_URL` =
  адрес этого координатора, видимый **с целевой машины**. Форма предзаполняет его
  из адреса, по которому admin открыл веб (`request.base_url`), но поле правится.
- Координатор должен достучаться до агента (стриминг/удаление файлов):
  `agent_url` = `http://<хост>:<порт>` цели. По умолчанию `http://<ssh-host>:8100`.
- Токен агента (`VIDHIVE_AGENT_TOKEN`) координатор подставляет из своих настроек,
  чтобы новый агент совпал с остальными. В форме не показывается.

## 4. Форма развёртывания (admin)

Поля: `ssh_host`, `ssh_port` (22), `ssh_user` (root); **вход по паролю
(`ssh_password`) ИЛИ по ключу (`ssh_key`, PEM)** — при аренде VPS обычно дают
IP + root-пароль; ни пароль, ни ключ не хранятся; `worker_name` (уникальное),
`threads` (8), `storage_path` (`/var/lib/vidhive/videos`); `agent_url`
(необязательно, по умолчанию `http://<host>:8100`). Адрес координатора не
запрашивается — берётся автоматически из `request.base_url` (тот адрес, по
которому админ открыл веб). Валидация: имя воркера `[A-Za-z0-9_-]`, порт
1..65535, путь абсолютный, host непустой, задан пароль или ключ.

## 5. Bootstrap-скрипт (`deploy/agent-bootstrap.sh`)

Идемпотентный, печатает шаги, exit≠0 при ошибке. Конфиг приходит через env
(координатор подставляет с `shlex.quote`). Действия:

1. Определить пакетный менеджер: `apt-get`/`dnf`/`yum`/`pacman`/`zypper`/`apk`.
2. Установить `python3`, `python3-venv`/`python3-pip`, `ffmpeg`, `git`.
3. `git clone`/`pull` репозитория в `INSTALL_DIR` (default `/opt/vidhive`).
4. Создать venv, `pip install ./common` + `pip install -r agent/requirements.txt`.
5. Записать env-файл (`/etc/vidhive-agent.env`) со всеми `VIDHIVE_*`.
6. Служба: если есть systemd — юнит `vidhive-agent.service` (EnvironmentFile,
   ExecStart = venv uvicorn, Restart=always) + enable+start; иначе fallback —
   `nohup` + pid-файл.

## 6. Teardown-скрипт (`deploy/agent-teardown.sh`)

Строго отменяет §5, печатает шаги, безопасен к повторному запуску:
`systemctl stop/disable vidhive-agent` (или kill по pid-файлу) → удалить юнит →
`daemon-reload` → `rm -rf INSTALL_DIR` → `rm -f` env-файл → `rm -rf STORAGE_PATH`
(«всё, что сделали»). Зависимости системы (python/ffmpeg) не трогаем — они могли
быть нужны и до нас.

## 7. Движок SSH (координатор)

`app/services/deployer.py` на `asyncssh`:
- `deploy(params, on_line)` — подключиться по ключу, залить скрипт, запустить с
  env, стримить stdout/stderr построчно в `on_line`, вернуть код возврата.
- `teardown(params, on_line)` — то же для teardown-скрипта.
- Все значения из формы — через `shlex.quote`. `known_hosts` не проверяем
  (первое подключение к новой машине), это осознанно для лабы.

Новая зависимость: `asyncssh` (в `coordinator/requirements.txt` и образ).

## 8. Данные

Таблица `agent_deployments` (миграция): `id`, `worker_id`→workers (nullable,
SET NULL), `ssh_host`, `ssh_port`, `ssh_user`, `install_dir`, `service_name`,
`storage_path`, `created_at`. Хранит **несекретные** данные (для teardown-формы и
пометки «развёрнут по SSH»). Ключ/пароль не хранятся никогда.

## 9. Живой лог развёртывания

- POST `/servers/deploy` (admin) валидирует форму, создаёт запись развёртывания
  в памяти (`deployments[id] = {status, lines[]}`), запускает фоновую задачу
  `deployer.deploy(...)`, редиректит на `/servers/deploy/{id}`.
- Страница `/servers/deploy/{id}` показывает лог; фрагмент `/servers/deploy/{id}/log`
  опрашивается раз в 1с (или через общий SSE-`bus`) и дописывает строки; по
  завершении — статус «успех/ошибка».
- Состояние развёртываний — в памяти процесса (переживать рестарт не обязано).

## 10. Снос через веб

На `/servers` у сервера, помеченного «развёрнут по SSH», в диалоге удаления —
дополнительный вариант **«Полностью снести с машины»**: показывает поля host/port/
user (предзаполнены из `agent_deployments`) + ключ (вводится заново) → POST
`/servers/{id}/teardown` → фоновый `deployer.teardown(...)` со стримом лога →
по успеху удаляет запись деплоя и Worker (как обычный delete). Прежние варианты
(«с данными» / «распределить») остаются.

## 11. Безопасность

- Только `administrator`. SSH-ключ/пароль не пишутся в БД/логи/URL; в памяти
  развёртывания хранится только лог (без секретов — скрипт не печатает env).
- Экранирование всех подставляемых значений (`shlex.quote`) — защита от инъекций.
- `known_hosts` не проверяем (лабораторный стенд, доверенная сеть) — задокументировано.

## 12. Тестирование

- Юнит: валидация формы; `deployer` с **замоканным** asyncssh (проверяем
  сформированную команду, экранирование, разбор кода возврата и стрима строк);
  запись `agent_deployments`; teardown-флоу с моком.
- Скрипты `agent-bootstrap.sh`/`agent-teardown.sh` — `bash -n` (синтаксис) в CI.
- E2E — на реальном Linux-сервере пользователя: развернуть агента, увидеть online,
  затем снести.

## 13. Открытые ограничения

- Alpine/OpenRC — fallback на nohup (без автозапуска после ребута).
- Цель должна иметь интернет (apt/pip/git) и права (root или passwordless sudo).
- Один агент на сервер (имя `vidhive-agent`, фикс. пути).
